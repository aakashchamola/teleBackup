# M7: Family release

> **Status (2026-11-02):** Done: release signing config that refuses without a key, R8 rules and a release build that works, `docs/RELEASES.md`, `docs/FAMILY_GUIDE.md` (draft), `docs/IOS_NOTES.md`. **Not done:** the signing key (owner), a real release, the family test, roll-out.

**Goal:** a signed APK the family can install and update, with a short guide. After this, iOS is considered.

**Done when:** a signed release APK (version 1.0.0) is installed on every family phone; each person finished setup alone using the guide; updating from 1.0.0 to 1.0.1 keeps their rules and history; the signing key is backed up by the owner; pushed.

## Before you start
- [ ] M6 done. Real delete has run on at least one real rule (Screenshots) on the owner's phone for a week with no surprises.

## Tasks

### 1. Signing key (the owner's job, guided)
- [ ] Owner makes the key on their own computer: `keytool -genkeypair -v -keystore ~/keys/telebackup-release.jks -keyalg RSA -keysize 4096 -validity 10000 -alias telebackup`.
- [ ] The `.jks` file and its passwords stay **outside the repo**. `app/android/key.properties` (git-ignored) points to it.
- [ ] Owner backs up the `.jks` and passwords somewhere safe (password manager + offline copy). **If the key is lost, the family can only update by uninstalling, which wipes the app's record of what was backed up.**
- [ ] `build.gradle.kts`: `signingConfigs.release` reads `key.properties` if present; release build fails clearly if missing.

### 2. Release build
- [ ] Release build excludes S-DEV, time warp, fault injection and debug base URL (they are in the `debug` source set; verify with `apkanalyzer` or by searching the APK's dex for "timeWarp").
- [ ] R8/ProGuard: keep rules for TDLib (`-keep class org.drinkless.tdlib.** { *; }`), kotlinx-serialization DTOs, Pigeon classes. Test the release build on the phone end to end (setup, upload, review, delete) because R8 issues only show there.
- [ ] TDLib logging off, `Tlog` verbose off in release.
- [ ] `flutter build apk --release --split-per-abi`; use the `arm64-v8a` APK (and `armeabi-v7a` only if a family phone needs it).
- [ ] Version: `pubspec.yaml` `version: 1.0.0+1` (name+code). Every release bumps both; code always goes up.
- [ ] `docs/RELEASES.md`: one entry per version (date, what changed, APK sha256).

### 3. Distribution
- [ ] The repo is private, so family members cannot download from GitHub. Share the APK through the owner's Telegram (send the APK file to each person), or a private Drive link.
- [ ] Each APK's SHA-256 is in RELEASES.md and in the message, so a family member (or the owner) can check it.

### 4. Family guide
- [ ] `docs/FAMILY_GUIDE.md` (and a copy as a PDF or Telegram message): with M5 screenshots. Sections: install (allow "Install unknown apps" for Telegram/Files), open and follow setup, what the notification means, Pause/Delay, how to find photos in Telegram (topics, `#tb` search), what "upload & delete" means and how to turn it on safely, how to update, what to do if Home shows a warning.
- [ ] Plain short words; test it on one family member who has not seen the app.

### 5. Updates
- [ ] Install 1.0.0, set up, back up a few files; build 1.0.1 (a tiny change); install over it: rules, history, login, queue all kept.
- [ ] Database migration test from 1.0.0's schema exists if the schema changed.
- [ ] Optional (not v1 unless the owner wants it): an "update available" check. v1 = the owner sends new APKs.

### 6. Roll-out
- [ ] One family phone first, a week, then the rest.
- [ ] Every rule starts upload-only (it is the default); each person turns on delete themselves after a week, per the guide.

### 7. After release
- [ ] Session log, tag `v1.0.0`, push tags.
- [ ] Write `docs/IOS_NOTES.md`: what an iOS version could do (upload only, no silent delete, background limits), so the owner can decide.
